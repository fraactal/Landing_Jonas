# Spec 011 - FAQ

## Estado

Implementada.

Esta spec define la seccion `Preguntas frecuentes` de `jonathanvaldes.com`. Fue implementada tras aprobacion explicita, con acordeon accesible, JavaScript minimo, sin dependencias, sin CTA final, sin Footer y sin contacto real.

## 1. Objetivo

Definir la futura seccion `Preguntas frecuentes` de la landing comercial.

La seccion debe reducir friccion antes del CTA final, responder dudas comerciales comunes y mantener un tono directo, profesional y transparente.

## 2. Contexto

La landing ya cuenta con navbar, hero, problema dinamico, selector de problemas, servicios, proceso, Demo / PoC, casos y Sobre mi.

FAQ funciona como una etapa de aclaracion previa al cierre comercial. No debe abrir nuevos flujos, prometer condiciones no definidas ni reemplazar una conversacion inicial.

## 3. Ubicacion

La seccion debe ubicarse inmediatamente despues de `Sobre mi` y antes de la futura seccion de CTA final.

Orden esperado:

```text
Sobre mi
FAQ
CTA final
```

## 4. Anchor

La seccion debe usar:

```html
id="faq"
```

Esto permite que el enlace `FAQ` del navbar funcione correctamente mediante `href="#faq"`.

## 5. Alcance

La implementacion futura debe incluir:

- seccion `Preguntas frecuentes`;
- siete preguntas frecuentes;
- respuestas breves;
- acordeon simple;
- preguntas visibles desde el inicio;
- respuestas cerradas inicialmente;
- apertura/cierre por click, tap y teclado;
- soporte para multiples preguntas abiertas simultaneamente;
- estados accesibles con botones reales;
- transiciones discretas compatibles con reduced motion.

## 6. Fuera de alcance

No implementar en este modulo:

- CTA final;
- Footer;
- contacto real;
- formulario;
- agenda;
- WhatsApp real;
- backend;
- analytics;
- paginas legales;
- tracking de interaccion;
- contenido dinamico remoto;
- modales;
- carruseles;
- sticky behavior.

## 7. Preguntas y respuestas

### 1. ¿Con que tipo de empresas trabajas?

Principalmente con empresas pequenas y medianas que necesitan resolver un problema tecnologico concreto, mejorar un proceso o construir una solucion sin ampliar innecesariamente su equipo interno.

### 2. No se exactamente que tecnologia necesito. ¿Eso es un problema?

No. Lo importante es entender primero que necesitas resolver. A partir de eso evaluamos las alternativas y proponemos una solucion proporcional al problema.

### 3. ¿Trabajas solamente con proyectos grandes?

No. Podemos abordar desde una integracion o automatizacion puntual hasta una aplicacion, plataforma o etapa mayor de modernizacion tecnologica.

### 4. ¿Siempre hay que construir una solucion completa desde el inicio?

No necesariamente. Cuando el caso lo permite, podemos validar primero una parte critica mediante una prueba de concepto acotada antes de avanzar con un desarrollo mayor.

### 5. ¿Como se define el costo de un proyecto?

Despues de entender el problema definimos alcance, entregables y complejidad. Con esa informacion podemos estimar costos y acordar una forma de trabajo clara antes de comenzar.

### 6. ¿Trabajas directamente en el proyecto?

Si. Trabajas directamente conmigo durante el proceso. Cuando un proyecto requiere capacidades adicionales, podemos incorporarlas de forma explicita segun la necesidad.

### 7. ¿Que necesito para conversar sobre mi proyecto?

Solo una explicacion simple del problema, proceso o idea que quieres resolver. No necesitas llegar con documentacion tecnica ni una solucion definida.

## 8. Tono

El tono debe ser:

- directo;
- simple;
- profesional;
- transparente;
- sin lenguaje promocional exagerado;
- sin promesas de resultados no documentados.

Las respuestas deben mantenerse breves, idealmente en una o dos frases.

## 9. Modelo de acordeon

Cada item debe incluir:

- pregunta visible;
- control visual de apertura/cierre;
- respuesta colapsable;
- separacion visual clara entre preguntas.

El patron visual recomendado es una lista sobria con bordes finos o separadores horizontales. Se pueden usar superficies ligeras si mantienen la estetica premium y no vuelven la seccion densa.

No usar cards pesadas para cada FAQ salvo que el resultado visual sea claramente mejor que una lista editorial.

## 10. Estrategia tecnica

Se evaluo la alternativa de usar `<details>` / `<summary>` por su soporte nativo para disclosure y su menor necesidad de JavaScript.

La estrategia recomendada para la implementacion es usar botones reales con JavaScript minimo porque ofrece mayor control visual, consistencia con el sistema actual y manejo explicito de `aria-expanded` / `aria-controls`.

La implementacion futura debe:

- mantener todas las preguntas y respuestas en el HTML inicial;
- usar un `<button>` por pregunta;
- asociar cada boton con su panel de respuesta;
- actualizar `aria-expanded` al abrir o cerrar;
- controlar el icono o indicador visual desde el estado del item;
- evitar listeners de scroll;
- no agregar dependencias.

## 11. Estado inicial

Al cargar la pagina:

- todas las preguntas deben estar visibles;
- todas las respuestas deben iniciar cerradas;
- ninguna respuesta debe anunciarse automaticamente;
- no debe existir `aria-live`.

## 12. Comportamiento multiple

La implementacion debe permitir que multiples preguntas permanezcan abiertas al mismo tiempo.

No debe cerrarse automaticamente una pregunta al abrir otra, salvo que una spec posterior cambie explicitamente esta decision.

## 13. Accesibilidad

Requisitos:

- usar botones reales para las preguntas;
- cada boton debe tener `aria-expanded`;
- cada boton debe tener `aria-controls` apuntando al panel correspondiente;
- cada panel debe tener un identificador unico;
- el contenido de respuesta debe permanecer en el DOM;
- no usar `aria-live`;
- mantener orden DOM logico;
- asegurar focus visible;
- permitir operacion con teclado;
- no depender solo del color para indicar estado;
- evitar que el foco quede atrapado.

El indicador visual puede ser `+ / -` o chevron, pero el estado accesible debe depender de `aria-expanded`, no solo del simbolo.

## 14. Reduced motion

Con `prefers-reduced-motion: reduce`:

- evitar transiciones de movimiento;
- mantener apertura y cierre inmediatos o con cambios no animados;
- no usar animaciones continuas.

En modo normal se permite una transicion breve de 200 a 300 ms, preferentemente con opacidad y/o altura controlada sin generar saltos bruscos.

## 15. Responsive

Mobile first:

- una columna;
- preguntas legibles;
- suficiente area tactil;
- respuestas con ancho completo;
- sin overflow horizontal.

Desktop:

- mantener lectura comoda;
- ancho contenido controlado;
- suficiente espacio negativo;
- alineacion coherente con las secciones anteriores.

El comportamiento debe ser el mismo en mobile y desktop.

## 16. Performance

La seccion debe resolverse con:

- HTML;
- CSS existente;
- JavaScript vanilla minimo.

No agregar:

- librerias;
- dependencias;
- imagenes;
- fuentes nuevas;
- listeners continuos;
- calculos costosos por frame.

## 17. Navegacion

El enlace del navbar `FAQ` debe apuntar a:

```html
href="#faq"
```

La implementacion futura solo debe verificar este enlace. No debe modificar anchors de secciones futuras.

## 18. Criterios de aceptacion

La implementacion futura se considera aceptada si:

- existe una seccion con `id="faq"`;
- aparece despues de `Sobre mi` y antes del CTA final;
- el titulo visible es `Preguntas frecuentes`;
- contiene exactamente las siete preguntas definidas en esta spec;
- las respuestas usan el copy aprobado;
- las preguntas estan visibles al cargar;
- las respuestas inician cerradas;
- cada pregunta se controla con un boton real;
- cada boton actualiza `aria-expanded`;
- cada boton referencia su respuesta con `aria-controls`;
- se permite tener multiples respuestas abiertas;
- no se usa `aria-live`;
- funciona con teclado;
- respeta `prefers-reduced-motion`;
- no modifica el comportamiento existente de navbar, M04, M05 ni M07;
- no agrega dependencias;
- no implementa CTA final, footer ni contacto real.

## 19. Archivos previstos

Para implementar esta spec se preve modificar:

- `index.html`;
- `assets/css/sections.css`;
- `assets/js/main.js`;
- `specs/011-faq.md`.

No se preve crear nuevas hojas CSS ni nuevos archivos JS.

## 20. Riesgos / deuda tecnica

- El FAQ depende de contacto real en modulos posteriores para cerrar el flujo comercial.
- Las respuestas pueden requerir ajuste futuro cuando existan politicas comerciales mas especificas.
- La decision de permitir multiples respuestas abiertas debe mantenerse simple; si luego se requiere comportamiento tipo acordeon exclusivo, debera documentarse en una spec posterior.
- El copy evita promesas comerciales cerradas porque todavia no hay condiciones publicas de servicio, precios ni SLA documentados.

## 21. Validaciones minimas

Al implementar esta spec se debe validar:

- `id="faq"` presente;
- siete preguntas exactas;
- copy aprobado;
- respuestas cerradas inicialmente;
- uso de botones reales;
- `aria-expanded` y `aria-controls`;
- ausencia de `aria-live`;
- comportamiento con multiples respuestas abiertas;
- soporte teclado;
- reduced motion;
- ausencia de dependencias nuevas;
- ausencia de CTA final, footer y contacto real;
- `node --check assets/js/main.js`;
- `git diff --check`.
